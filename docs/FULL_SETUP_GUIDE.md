# MedPrep BCQs: complete MongoDB setup and running guide

This guide runs the source supplied in this ZIP. It uses Next.js with a Node.js backend and the official MongoDB driver. You can use MongoDB Atlas without installing MongoDB locally, or use the included Docker replica set. Choose one database option.

The existing hosted review app is separate and still uses its original SQL database. Installing this ZIP creates your own MongoDB application. Existing hosted accounts, questions, payments and receipts are not automatically transferred. There are no real student records, passwords, payment account numbers or medical questions in this archive.

## 1. Install the tools

Install Node.js 22.13 or newer from https://nodejs.org/ and optionally VS Code from https://code.visualstudio.com/. Open a new terminal after installation. On Windows, use Command Prompt or PowerShell. Check:

```sh
node --version
npm --version
```

For the Docker option also install and start Docker Desktop, then check:

```sh
docker --version
docker compose version
```

If PowerShell blocks npm.ps1, run the commands in Command Prompt or use `npm.cmd` in place of `npm`. You do not need to change the application's source.

## 2. Extract and open the source

Extract MedPrep-BCQs-MongoDB-Setup.zip. Open the **MedPrep-BCQs-MongoDB** folder in VS Code. In Terminal → New Terminal, confirm this folder contains package.json, package-lock.json and .env.example.

```sh
npm ci
npm run setup:env
```

The first command installs the locked dependencies. The second creates a private `.env` with fresh CNIC encryption and administrator setup secrets. It will not overwrite an existing `.env`.

Keep these generated values private. Keep CNIC_KEY stable after enrollment begins; changing it prevents decryption of existing CNIC values.

## 3A. Connect MongoDB Atlas

1. Open https://cloud.mongodb.com/, create an Atlas account if needed, and create a project and database deployment.
2. Create a **database user** with a strong password. This is separate from your Atlas website login and separate from the MedPrep administrator account.
3. Give the database user read/write permissions on your application's `medprep` database and permissions required to create collections, indexes and validation rules. Initialize with a trusted database administrator if you use a more restricted runtime user.
4. Add your current machine's public IP to the project's network/IP access list. When deploying later, authorize the server's outgoing address too.
5. Open the database's Connect workflow, choose the Node.js driver connection method and copy the supplied `mongodb+srv://...` URI.
6. Open `.env` and replace MONGODB_URI with that URI, filling in the database username and password. URL-encode special characters in the password when building a URI. Retain the actual host returned by Atlas; the sample below is only a placeholder.

```dotenv
MONGODB_URI=mongodb+srv://YOUR_DB_USER:YOUR_ENCODED_PASSWORD@YOUR_CLUSTER_HOST/medprep?retryWrites=true&w=majority
MONGODB_DB=medprep
```

Leave CNIC_KEY and ADMIN_SETUP_TOKEN at the values generated by setup:env. Keep PROOF_STORAGE_DIR=./private-uploads for local use. Restart the application after changing environment settings.

Atlas requires both a database user and an authorized connecting IP. Official connection instructions: https://www.mongodb.com/docs/atlas/connect-to-database-deployment/.

Continue to step 4. You do not need Docker for this option.

## 3B. Run MongoDB locally with Docker

From the application folder, run:

```sh
docker compose up -d
docker compose ps
docker compose logs mongo-init
```

The supplied compose file starts MongoDB and initializes the local `rs0` replica set. It exposes the database only on your machine's loopback address. The generated `.env` already contains:

```dotenv
MONGODB_URI=mongodb://127.0.0.1:27017/medprep?replicaSet=rs0&directConnection=true
MONGODB_DB=medprep
```

This Docker configuration is for local development. Use authenticated, protected MongoDB infrastructure for production. Its named volume preserves data when you stop the containers. Use `docker compose stop` to stop the local database and `docker compose start` to start it again. Do not remove the database volume if you want to preserve records.

A replica set is required because payment approval, access activation, password reset and account deletion use transactions. A plain standalone MongoDB installation is insufficient. Official transaction deployment guidance: https://www.mongodb.com/docs/manual/core/transactions-production-consideration/.

## 4. Initialize collections and verify the database

```sh
npm run db:init
```

Expect: **MongoDB collections, validators and indexes ready.** This command creates the collections/indexes and core validation rules without seeding real content. It is safe to run again against an already initialized database.

The collections include users, profiles, sessions, resets, packages, payments, subscriptions, questions, categories, attempts, bookmarks, notifications, audit, settings and limits. Accounts are stored in `users`; enrollment in `profiles`; payment receipts are private files, with their references in `payments`.

For Docker, if initialization starts before the replica set is ready, wait a few seconds and retry. For Atlas, verify your IP access entry, database credentials and database-user permissions if it fails.

## 5. Start the application

```sh
npm run dev
```

Open http://localhost:3000. Then open http://localhost:3000/api/health. A successful response reports `status: healthy` and `database: mongodb` inside the `data` object. If port 3000 is occupied, stop the other service or run:

```sh
npm run dev -- --port 3001
```

Use http://localhost:3001 for that run. Keep the terminal running while using the application. Press Ctrl+C to stop it.

## 6. Create your administrator

1. On the login screen click **Administrator setup**.
2. Enter the administrator's name, email, mobile and a password of at least 10 characters.
3. Copy the **ADMIN_SETUP_TOKEN from your own `.env`** into the setup-code field.
4. Submit the form, then sign in with the email and password you just chose.
5. The application opens **Admin dashboard**. It does not ask an administrator to enroll or submit payment.
6. Once setup succeeds, clear ADMIN_SETUP_TOKEN in `.env` and restart the server. The first administrator already exists, and new admin setup is blocked.

The earlier hosted review setup code does not apply to this installation. This version supports one administrator account.

## 7. Configure packages, payments and content

In Admin dashboard:

- **Packages:** create a package, enter the price, duration and permitted years/subjects/modules, and make it active. The API stores prices in PKR paisa; the package UI accepts a rupee price.
- **Payment accounts:** enter your actual JazzCash, Easypaisa and/or NayaPay account title and number, then enable the method. Unconfigured methods remain unavailable.
- **Categories:** define the academic year, subject, module and topic paths.
- **Questions:** create questions manually or use the JSON/CSV templates in templates/. Preview imports, correct errors, commit the import as drafts, review the answers/explanations, then publish.
- **Branding:** adjust the name and support link if desired.

The templates contain a nonmedical format demonstration only. They are not MBBS learning content. Students see only published questions within their approved package scope.

## 8. Test the full student workflow

Use a separate student account, preferably in another browser profile to keep the admin session available.

1. Register and log in as a student.
2. Complete the CNIC, college and MBBS-year enrollment form.
3. Select your configured package and payment method.
4. Submit the transaction details and a matching JPG/PNG/PDF receipt of at most 5 MB.
5. Confirm that the student sees pending review and has no BCQ access yet.
6. Log in as administrator and review the submission. A proof upload alone never grants access.
7. Approve the submission, then return to the student account. Access should be active.
8. Start practice using published matching questions. Submit an answer and review its explanation.
9. Start a module/final exam, save answers and refresh. The server deadline should stay unchanged.
10. Submit the exam and check Results & progress.

Use nonmedical demonstration content and clearly marked test payment details for testing. Replace them with your reviewed sources and real payment configuration when ready.

## 9. Account deletion and audit history

Students use **My profile → Delete account**, enter their current password, and confirm in the application's confirmation window. Administrators use **Students → Remove student** and confirm the displayed student.

Deletion removes the account and student-owned enrollment, payment records, receipts, subscriptions, bookmarks, study attempts, notifications, sessions and reset tokens. The deleted account cannot keep using its previous login session. Administrator accounts cannot be removed through the student-removal control.

The administrator-only audit keeps the student's name, account ID, who performed the deletion, the action and timestamp. It distinguishes student self-deletion from administrator removal. It does not keep the student's password or CNIC. Names absent from older audit records cannot be reconstructed after the account has already been removed.

If a private receipt cannot be deleted because storage is unavailable, a durable cleanup job remains. The administrator can use **Retry receipt cleanup** when shown in student management.

## 10. Run production mode locally

Stop the development server first, then run:

```sh
npm run typecheck
npm run build
npm start
```

Open the same local address. When code changes, stop the server, rebuild and start it again. For development you can use npm run dev instead.

To run automated verification:

```sh
npm test
```

The test uses a separate temporary real MongoDB replica set and does not use your production database. Its first run downloads a MongoDB binary. It checks the core workflow and named deletion audits.

## 11. Deploy to a Node.js server

Use a Node hosting service or VPS with persistent private storage. Set the same server environment variables there. Build with `npm ci && npm run build`; start with `npm start`. Initialize the deployed database before use with `node scripts/init-db.mjs` when the hosting platform has already set environment variables.

Use HTTPS and an authenticated MongoDB deployment. Mount a persistent disk and set PROOF_STORAGE_DIR to its private absolute path, such as `/var/data/medprep`. Never expose this directory through a public/static route. A temporary server filesystem will lose receipts on redeployment.

This proof adapter assumes one app instance. Multiple instances need shared private file/object storage. Back up the database, proof files and CNIC encryption key together. See docs/DEPLOYMENT.md for proxy settings and optional reset-email delivery.

## 12. Troubleshooting

| Problem | What to check |
| --- | --- |
| node/npm command not found | Install Node.js and reopen the terminal. |
| package.json not found | Open the extracted MedPrep-BCQs-MongoDB folder before running npm. |
| Missing MONGODB_URI | Run setup:env, edit .env and restart. |
| Database connection timeout | Check Atlas IP access, credentials, host, DNS and firewall; or start Docker. |
| Transaction/replica-set error | Use Atlas or the included Docker replica set, then run db:init. |
| Administrator already configured | Sign in with the existing admin account rather than using setup again. |
| Payment method unavailable | Configure and enable the actual account title and number. |
| No questions available | Publish questions and match the student's year, filters and package scope. |
| Delete account rejected | Enter the current password; review the visible message in the confirmation window. |
| Receipts missing after redeployment | Configure a persistent private disk and restore your backed-up files. |
| Reset email unavailable | Configure the reset delivery service or use an admin-issued single-use reset link. |

Keep .env and receipts private when sharing source code. The ZIP includes only .env.example and source files, not your real secrets or database contents.
